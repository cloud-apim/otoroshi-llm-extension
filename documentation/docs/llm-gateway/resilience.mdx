# Resilience

Resilience ensures that LLM interactions remain highly available and fault-tolerant, even when providers experience outages or failures.

## Key Features

- **Load Balancing**: Distribute requests across multiple providers to optimize performance and availability. See [Load Balancing](/docs/llm-gateway/loadbalancing).
- **Provider targets**: Spread one provider over several copies of its server, and let your monitoring tell the gateway which ones can take more work. See [Provider targets](/docs/llm-gateway/provider-targets).
- **Smart Routing**: Let the gateway pick the model for each request, and cascade to the next best one on failure. See [Otoroshi Router](/docs/llm-gateway/otoroshi-router).
- **Fallback Mechanism**: Automatically switch to alternative LLM providers in case of failures. See [Fallback](/docs/llm-gateway/fallback).
- **Rate Limiting & Quotas**: Prevent overloading a single provider by distributing usage effectively. See [Quotas](/docs/cost-optimizations/quotas).

## Load Balancing

The load balancer is a virtual provider that distributes requests across multiple providers using configurable strategies (round robin, random, best response time).

[Read the full Load Balancing documentation](/docs/llm-gateway/loadbalancing)

## Provider targets

A provider can have several targets: copies of the same server, one picked for each call among those that can take
it, another one answering when the first fails. Your monitoring tool pushes the state of each target (`available`,
`saturated`, `draining`, `down`), and a full server stops getting new work before your users wait in its queue.

[Read the full Provider targets documentation](/docs/llm-gateway/provider-targets)

## Timeouts

A provider has two timeouts, both in its `connection`:

```js
"connection": {
  "base_url": "https://gpu-1.internal:8443/v1",
  "timeout": 300000,
  "ttft_timeout": 30000
}
```

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `timeout` | number | `180000` | Bounds the whole call, streamed answer included, in milliseconds |
| `ttft_timeout` | number | — | For streamed calls: how long to wait for the first token, in milliseconds |

Both run from the start of the call. Once the first token came, only `timeout` applies: with the values above, an
answer can stream for five minutes, but a server that has not produced a single token after 30 seconds is given up.
The call to it is cancelled and its connection closed, and since nothing was sent to the caller yet, the
[fallback](/docs/llm-gateway/fallback) of the provider answers instead. A server that keeps missing the deadline
opens its circuit, so the next calls go to the fallback without waiting.

What counts as a first token is something the caller would see: content, reasoning or a tool call, not the empty
`role: assistant` chunk some servers start with. When the gateway runs the tools of the call itself, the first tool
call of the model is its first token: a slow tool is never taken for a slow provider.

:::tip Keep it large
The first token of a long prompt takes time to come, even on a healthy server: a tight `ttft_timeout` gives up calls
that were about to be answered, and has them computed again elsewhere. It is a safety net against a server that
hangs. To keep the calls away from servers that are full, push their state with [provider targets](/docs/llm-gateway/provider-targets).
:::

A call given up this way fails with:

```json
{
  "error": {
    "type": "first_token_timeout",
    "code": "first_token_timeout",
    "message": "no token from provider 'Mistral on premises' within 30000 ms"
  },
  "status": 504
}
```

and is counted in the `ai.first_token_timeouts` metric.

## Smart routing

The Otoroshi Router is a virtual provider that picks the model for each request: the cheapest model that codes well enough (`code-router`), the best model for each prompt (`auto-router`), or a panel of models answering together (`fusion-router`). When the selected model fails, the next best candidate answers.

[Read the full Otoroshi Router documentation](/docs/llm-gateway/otoroshi-router)

## Fallback

The fallback mechanism automatically retries failed requests on an alternative provider, ensuring service continuity.

[Read the full Fallback documentation](/docs/llm-gateway/fallback)

## Provider errors

When a provider rejects a call, the client gets the provider's own error, with its message and details, instead of a
generic gateway error. This holds for streamed calls too, whatever the size of the error or the pace at which the
provider sends it, and for errors that are not json (an html page from a load balancer in front of the provider, for
instance), which are returned with their status:

```json
{
  "status": 503,
  "body": "<html><body><h1>503 Service Unavailable</h1></body></html>"
}
```

The error is also logged, so you can see why a provider refuses a request. The errors of streamed calls are read up to
4 MB, enough for validation errors that echo a whole conversation, and the rest is dropped:

```hocon
providers {
  max-error-body-size = 4M
  max-error-body-size = ${?CLOUD_APIM_EXTENSIONS_LLM_EXTENSION_PROVIDERS_MAX_ERROR_BODY_SIZE}
}
```

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `max-error-body-size` | size | `4M` | Maximum size of an error body read from a streamed provider call |
